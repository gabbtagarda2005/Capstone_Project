# Settings Module — Component Documentation
### Bukidnon Bus Company @BUKSU — Administrator Module

*Every claim below is traced to the actual frontend and backend implementation through direct source-code inspection. Where a setting is saved but not actually read or enforced anywhere else in the system, that distinction is stated explicitly rather than left to the setting's name or description to imply otherwise.*

---

**Settings Module Overview.**
The Settings module is where an administrator configures system-wide preferences rather than day-to-day operational records — covering regional display preferences, account security policy, the company's branding information, and which parts of the companion mobile and web applications are intended to be visible. Unlike most of the system's other administrative screens, the values configured here are not tied to a single administrator's own account; with one specific exception described below, they are stored centrally and apply to the system as a whole, for every administrator who opens the page.

**Settings Navigation.**
The module is organized into four tabs — General, Security, Branding, and App Access — each with its own content and, in most cases, its own independent save action, meaning a change made in one tab is not submitted together with changes in another; each tab must be saved on its own. Every tab is reachable by any signed-in administrator, though, as described under Security and Branding below, whether a given tab's save action is actually available to that administrator depends on their assigned access level.

**Regional Settings.**
A section labeled "Regional" exists, but it is narrower than its name might suggest: in the current implementation, it groups together exactly three controls — the interface's light/dark appearance, the selected timezone, and a delay-threshold figure used elsewhere in the system — rather than offering a full set of regional preferences such as language or date-format selection. A currency value is stored internally alongside these settings and is always saved as Philippine pesos, but there is no interface control for it at all; the administrator cannot currently view or change it, and nothing elsewhere in the system reads this value back out for any purpose.

**Appearance Settings.**
The administrator can switch the interface between a light and a dark visual theme, with the choice taking effect immediately as soon as it is selected. This preference is saved only to the device and browser currently being used, rather than being sent to and stored by the central system — it is not part of the same settings record that the rest of this module saves. As a result, the chosen appearance will be remembered the next time the same administrator signs in on the same device and browser, but it will not follow them to a different computer or browser, where the appearance would instead reflect whatever that device's own browser last had set, or the system default if nothing was ever set there before.

**Timezone Settings.**
A dropdown lets the administrator choose a reference timezone for the system from a list that includes Manila, Singapore, Hong Kong, Shanghai, Tokyo, Seoul, Dubai, Mumbai/Kolkata, London, Paris, New York, Los Angeles, Sydney, Auckland, and a plain Coordinated Universal Time option. It is important to describe precisely how much of the system this selection actually governs, because the answer is narrower than the setting's prominence in the interface would suggest. Changing this value does genuinely affect two specific things: how the time is formatted in the alert message sent to administrators during an emergency SOS notification, and how the reporting day boundary and displayed timestamps are determined for the automated daily operations report. Beyond those two uses, however, every other time-sensitive part of the system — including estimated-time-of-arrival calculations, the determination of "today" for schedules and dispatch, and the time grouping used throughout the reporting and analytics module — is fixed to Philippine time regardless of what is selected here. In other words, this setting is saved and does have a real, if limited, effect, but it should not be assumed to retime the system as a whole; outside its two confirmed uses, the rest of the system behaves as though this setting were always left at its Philippine default.

**Delay Threshold Settings.**
This numeric field, expressed in minutes, is described in the interface as feeding the system's smart estimated-time-of-arrival feature, specifically governing when a bus should be treated as running late. The value can be set anywhere from one to one hundred eighty minutes, and the figure genuinely is saved and read back by several parts of the system — it is not purely cosmetic. There are two important limitations worth stating plainly, however. First, most of the places that read this saved value will only actually honor it if it is set to exactly eight, ten, or twelve minutes; any other value the interface otherwise permits the administrator to enter will be silently treated as the default of ten minutes by those parts of the system, without any warning to the administrator that their chosen value was not applied as entered. Second, and separately, the specific tiers the system uses elsewhere to classify a bus as only slightly delayed, moderately delayed, or severely delayed are governed by their own fixed set of time boundaries built directly into that classification logic, and do not reference this setting at all — so changing this delay threshold does not change how the system labels the severity of a delay, only certain narrower behaviors such as flipping a scheduled trip's status or triggering a traffic alert to the attendant.

**Save General Settings.**
The General tab's save action submits the timezone, the currency value described above, the delay threshold, and two notification-related toggles together as one update. Two older-style preferences — an email daily-summary option and a sound-alert option — have no visible control anywhere on this tab, yet the save action quietly includes both of them, turned off, every time General settings are saved; an administrator saving any other General setting will also be resetting these two to off, without being shown that this is happening. After saving, the interface shows a brief on-page confirmation message that clears itself automatically after a few seconds; if the save instead fails, the same message area is used to show the error text, but it uses the same visual styling as a successful save and does not clear itself automatically, remaining on screen until the next save attempt. These values are stored centrally rather than on the administrator's own device, so — apart from the separately handled appearance preference described above — they persist after a page refresh and after a full sign-out and sign back in, for every administrator who opens the page.

**Security Settings.**
This tab governs account-protection policy and is organized into separate controls for Bus Attendant accounts and Administrator accounts, each with its own save action, alongside a shared idle-session-timeout figure (five to four hundred eighty minutes) that applies to both. Beyond the login-attempt limit and lockout duration already described elsewhere in this documentation, the tab includes a toggle for each account type controlling whether this security policy is actually applied to that type of account at all, and a dedicated incident-alerts area containing live SOS-incident controls alongside two further toggles: one for showing an on-screen alert when a geofence boundary is breached, and one labeled as requiring confirmation before a sensitive action is performed elsewhere in the system. The login-attempt, lockout-duration, idle-timeout, policy-application toggles, and the geofence-breach alert are all genuinely read and acted upon elsewhere in the system, confirmed by locating where each one is actually consumed. The sensitive-action confirmation toggle, however, saves successfully and is retained exactly like the others, but — despite its description — nothing elsewhere in the system currently reads it back or changes its behavior based on it; no confirmation step anywhere in the administrator interface is currently gated by this setting. Every control in this tab is restricted to the highest administrator privilege level; any other administrator, including one with view-only access, sees these controls locked and is shown a message explaining that only that top privilege level may make this kind of change, and the restriction is enforced by the system itself, not only by hiding the controls on screen.

**Branding Settings.**
This tab lets the administrator set the company's name, contact email and phone number, physical location, a logo (either uploaded directly or linked by web address), and a footer line used on exported reports. Unlike several of the settings described above, this section is a fully working, centrally shared source of company information: once saved, the same details are read back and displayed not only within the Administrator Module itself, but independently by the Commuter-facing application and by the Bus Attendant mobile application, meaning a company-name or logo change made here is reflected consistently across all three parts of the system rather than remaining confined to the admin screen alone.

**App Access Settings.**
This tab presents individual switches for specific sections of the Bus Attendant app (such as its dashboard, ticketing, passenger-editing, notifications, and settings areas) and the Commuter app (such as its dashboard, schedules, bus-checking, news, and feedback areas), implying that an administrator can use these switches to show or hide those areas for end users. Based on a direct check of where these saved values are actually used elsewhere in the system, they are not currently enforced anywhere: no part of either the Bus Attendant app or the Commuter app currently reads these values back to restrict or hide anything, and toggling a switch off here does not currently prevent a user from reaching that part of either app. This matches what the interface's own explanatory text on this tab already states — that these values are being stored in preparation for a future update rather than taking effect today — but it is worth stating directly for documentation purposes: these controls should currently be understood as reserved for future use rather than as an active access restriction.

**Settings Persistence and Validation.**
With the single exception of the light/dark appearance preference, every setting described above is stored in one shared, centrally kept record rather than anything tied to an individual administrator's device or session, and reloading the Settings page — including after a full sign-out and sign back in — re-reads this same central record rather than showing anything left over from a previous visit. Numeric fields such as the delay threshold and the security timing values are range-checked both as the administrator types and again when the save action is submitted, preventing an out-of-range number from being saved even if it were somehow entered. When loading the page's settings fails, an error message is shown to the administrator in most cases, with one specific exception: a particular kind of failure indicating the settings service could not be reached in the expected way is deliberately suppressed rather than displayed, so an administrator encountering that specific failure would see the page load with no values and no visible explanation of why. As noted in the individual sections above, the Timezone, delay-threshold quantization behavior, sensitive-action confirmation toggle, and App Access toggles are the clearest examples of settings that appear fully functional in the interface but are only partially, narrowly, or not at all connected to the behavior they describe elsewhere in the system.

**Testing and Verification.**
This documentation was produced entirely through direct inspection of the system's source code, including deliberately searching for every other place in the codebase where each setting's saved value might be read back, in order to distinguish a setting that is genuinely acted upon from one that is saved but otherwise unused. No live browser testing of this module was performed, no automated or service-level tests were run, and no setting was independently confirmed by actually changing it on the live, deployed system and observing the result; every statement above describes what the implemented code is written to do, not a confirmed live observation.

## Documentation Summary

The Settings module gives the administrator a single place to configure the system's regional display preferences, account security policy, company branding, and intended application access — and, as documented above, the great majority of what it offers genuinely does what its labeling implies, including the account-lockout policy, idle-session timeouts, and the branding information shared consistently across all three parts of the system. A smaller but important set of exceptions is worth carrying forward into any evaluation of the system: the timezone selector governs only two specific behaviors rather than the system's time handling as a whole, the delay-threshold figure is honored only at a few specific values rather than across its full allowed range, one security toggle and the entire App Access tab currently save without being enforced anywhere, and one category of page-load failure is hidden from the administrator rather than shown. None of these findings suggest the module is broken — each saves and retrieves its values correctly — but an honest account of the system, which is the purpose of this documentation, requires describing precisely which settings currently change real system behavior and which are, for now, recorded without yet being acted upon.
