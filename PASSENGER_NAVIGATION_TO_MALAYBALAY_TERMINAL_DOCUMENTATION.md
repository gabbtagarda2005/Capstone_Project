# Passenger Navigation Feature — Walking Directions to a Selected Bus Terminal
### Bukidnon Bus Company @BUKSU — Passenger Module

*The explanation below is based on direct inspection of the system's source code for the Station Finder's navigation screen, using the example of a passenger navigating to Malaybalay Integrated Bus Terminal. It describes what the passenger sees, what each control does, and how the system actually produces the figures shown, written in plain, formal language for Chapter 4.*

---

**1. Navigation Feature.**
Once a passenger selects a terminal to walk to, the system switches from the list of nearby terminals into a dedicated navigation view built specifically for that trip. This view continuously reads the passenger's live device location and compares it against the chosen terminal's fixed coordinates, so that the distance and walking time shown are always relative to where the passenger currently is, not a single starting snapshot taken only once when navigation began. The system also keeps requesting an updated walking path from an external routing service as the passenger moves, so the guidance shown stays current with the passenger's actual progress rather than remaining fixed to the very first path calculated.

**2. Destination and Distance.**
One detail needs to be corrected against how the destination might be assumed to appear on screen: the navigation view's heading shows only the terminal's own registered name — "Malaybalay Integrated Bus Terminal" — and does not display the barangay or area name together with it, even though that area information does exist elsewhere in the system's records. The distance figure shown below the destination name is genuinely calculated, not a fixed example value: it is measured along an actual walkable path returned by an external routing service, and only falls back to a straight-line measurement between the two points if that service cannot be reached. The estimated walking time is also genuinely calculated rather than displayed as a sample figure, but it is deliberately computed in its own way rather than trusting the routing service's own time estimate: the system takes the real distance that service calculated and applies its own fixed, consistent walking pace to produce the number of minutes shown, because the particular routing service used is only reliable for calculating real walking paths and distances, not for estimating how long a person actually takes to walk them. For reference, a measured distance of 1.6 kilometers works out to almost exactly 20 minutes under this system's fixed walking pace, which is consistent with the figures described in this documentation.

**3. GPS Accuracy Warning.**
This warning appears specifically when the passenger's device reports a location accuracy worse than fifty meters, and its wording in the system matches exactly: "GPS accuracy is low. Move to an open area for a more accurate location." The system determines this by reading an accuracy value supplied directly by the passenger's own device alongside their coordinates, and comparing that value against the fifty-meter limit built into the system. The warning is purely informational — it does not pause, block, or otherwise interfere with the navigation, the calculated route, or the distance and time already shown; it simply lets the passenger know their displayed position may not be precise, typically because they are indoors, under heavy cover, or in an area with poor satellite visibility.

**4. Interactive Map.**
The map is built using Leaflet, an open-source mapping library, with its underlying imagery supplied by OpenStreetMap, whose required attribution text ("© OpenStreetMap contributors") is genuinely displayed on screen rather than omitted. The system displays more than just the destination and the passenger's current position: it draws an actual line representing the walking path between them, and this line is visually distinguished depending on its source — a confident, solid-colored line when it is a genuine, routing-service-calculated path, or a dashed, muted-colored line when it is only a straight-line approximation shown because a live route could not be obtained at that moment. The passenger's own position and the destination are each shown with their own distinct marker icon on the same map.

**5. Recenter Button.**
Pressing the Recenter button simply moves the map's view back to center on the passenger's current position and the destination together; it does not request a new route, recalculate the distance, or change the estimated walking time in any way. It exists purely to help a passenger who has panned or zoomed the map manually find their way back to a clear, centered view of their position and where they are heading.

**6. Cancel Navigation Button.**
Pressing Cancel Navigation fully clears the current navigation session — the selected destination, the walking path drawn on the map, and any arrival status are all reset together — and returns the passenger to the earlier list of nearby terminals. The map itself returns to the station-list view rather than remaining on screen in any partial or frozen state, and the passenger is free to choose the same terminal again or a different one without needing to restart the feature from elsewhere in the application.

**7. Limitations.**
Several practical limitations are worth stating plainly. The walking path shown is normally a genuine, real path-following route, but if the routing service cannot be reached or returns no usable path, the system automatically falls back to a straight-line estimate, clearly shown as a dashed line together with an on-screen notice explaining that a live route was unavailable. The system recalculates the walking path as the passenger moves, but only once they have drifted a meaningful distance — roughly sixty meters — from where the last path was calculated, and not more often than once every twelve seconds, specifically to avoid sending excessive requests to the routing service. Arrival detection and the distance figure both depend entirely on the passenger's device successfully reporting its location; if location access is denied, unavailable, or fails for any other reason, the navigation view shows a clear error message along with a button to try again, rather than silently failing or showing an inaccurate position. Finally, because the walking-time estimate is deliberately based on a fixed assumed walking pace rather than the passenger's actual walking speed, a passenger walking notably faster or slower than that assumed pace, or taking a path other than the one drawn, may find the real time taken differs somewhat from the estimate shown.

---

## Documentation Summary

The passenger navigation feature genuinely guides a commuter from their current position to a chosen terminal — here, Malaybalay Integrated Bus Terminal — using a real, continuously updated walking distance, a deliberately recalculated time estimate, and a path drawn on an open-source map, with honest on-screen notices whenever GPS accuracy is poor, a live route cannot be obtained, or location access is unavailable. The one correction worth carrying into the final paper is that the destination name shown during navigation does not include the barangay or area name alongside the terminal's own name, even though that detail exists elsewhere in the system's records.

## Testing and Verification

This documentation is based entirely on direct inspection of the system's source code, including the exact threshold values, wording, and calculation formulas used by the navigation feature. It has not been confirmed through actual use of the running application in a browser, and no live walking-navigation session to Malaybalay Integrated Bus Terminal was performed as part of producing this documentation; the 1.6-kilometer and twenty-minute figures are treated here as a worked example consistent with the system's own calculation method, not as independently measured results.
