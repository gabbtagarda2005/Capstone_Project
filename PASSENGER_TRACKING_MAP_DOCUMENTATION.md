# Passenger Tracking Map — Component Documentation
### Bukidnon Bus Company @BUKSU — Passenger Module

*Every claim below is traced to the actual frontend and backend implementation through direct source-code inspection. One architectural note worth stating up front: this documentation traces the actively maintained version of the passenger tracking experience, which is built directly into the Administrator frontend's own codebase and served from its `/passenger` and `/passenger/track` web addresses — this is the version matching what was actually observed on screen. A second, separate, older standalone build of a similar passenger application also exists elsewhere in the project but was not the basis for this documentation, since its interface does not match what was described; this is flagged here rather than silently assumed to be the same thing.*

---

**Interactive Map (SVG, Leaflet, and OpenStreetMap).**
The central map is built using Leaflet, an open-source mapping library, drawing its underlying map imagery from OpenStreetMap and related open map-tile sources rather than a commercial mapping service such as Google Maps — confirmed across every one of the map's four selectable styles (standard map, satellite imagery, terrain, and a dark-themed variant), each of which pulls from a different open tile provider. The required attribution text for these sources is genuinely displayed on screen, in the map's own default attribution corner, rather than omitted or substituted. On top of this base map, several distinct marker types are drawn using small custom icon graphics rather than images: a hexagonal marker for registered terminals, a small dot for intermediate bus stops, a dashed-ring marker for corridor waypoints, a bus emoji marker for each actively tracked vehicle, a pulsing dot representing the passenger's own detected location, and a pair of lettered start/destination markers that appear specifically once a bus's route has been selected. A circular boundary is also drawn around each terminal, reflecting that terminal's configured detection radius, the same style of boundary used elsewhere in the system to detect arrivals.

**Weather.**
This is not a separate page or report; it is a toggle control that turns a set of weather marker icons on and off directly on the same interactive map described above, rather than opening a distinct weather screen. When enabled, a weather-condition icon appears at each location the system monitors for conditions, and tapping one of these icons opens a small overlay panel showing the temperature, humidity, wind, and precipitation detail for that specific spot, explicitly labeled with how many minutes ago that reading was last refreshed rather than presented as instantaneous. This is a different feature from a separate weather-advisory summary that also appears elsewhere in the interface's news and alerts area; the two draw from related information but are reached and presented differently.

**Need Help?**
Despite its wording, this control does not open a contact form, a frequently-asked-questions page, or any live support channel. Selecting it reopens a short, multi-step onboarding guide — the same orientation walkthrough that is shown automatically the first time a passenger uses the tracking page — explaining, step by step, how to use the Quick ETA feature, the route and fare tool, the arrival-alarm feature, the station finder, the feedback form, and the lost-item report. A passenger wanting to actually submit feedback or report a lost item does so through the separate "Support" navigation option described below, not through "Need Help?"

**More.**
This control expands or collapses the small set of map-style choices — the standard map view, satellite imagery, terrain, and a dark theme — functioning purely as a display-preference control for how the map itself looks. It is unrelated to assistance, support, or any passenger-data feature.

**Company Header and Exit.**
The company name and logo shown at the top of the page are drawn from the same centrally configured company information used consistently across the system's other applications, rather than being fixed text specific to this page — a change made to the company's name or logo elsewhere in the system is reflected here as well. The Exit control does not sign the passenger out of an account, since the system does not require or support passenger accounts; instead, it clears this browser's saved location-sharing preference for the tracking page and returns the passenger to the application's landing screen.

**Live Network Map.**
The map labeled with the region name is the same interactive map described above, not a separate or simplified view — the label simply identifies the geographic area currently being tracked, and defaults to the company's home service area when no other region has been configured. It is important to describe precisely what "live" means here: bus positions are not pushed to the page through a continuously open connection, but are instead retrieved through the page repeatedly re-requesting the latest positions on a short, fixed interval — in practice, roughly every eighteen seconds — alongside separate, slower refreshes for terminal and stop information. This produces an experience that updates on its own without the passenger needing to refresh the page, but it should be understood as frequent automatic polling rather than an instantaneous live feed.

**Quick ETA, Trip Planner, Support, and Station Navigation.**
These four options are not separate pages that reload the application; they are four switchable sections of the same single tracking screen, presented as floating buttons the passenger can tap to change what is shown without leaving the map view. Quick ETA, described in detail below, lists upcoming buses by estimated arrival time. Trip Planner — despite its name — does not plan a full multi-step journey with transfers; it is a fare calculator that lets a passenger choose a starting point and a destination from the system's registered terminals and stops, select a passenger category such as regular, student, senior citizen, or person with disability, and receive a computed fare for that specific trip, and it also contains the controls for setting an arrival alarm. Support presents a feedback form and a lost-item report form side by side, letting a passenger submit either directly from this screen. Station opens a separate, smaller embedded map of its own, which ranks the system's registered terminals by distance from the passenger's current location and, once one is selected, can generate a walking route to it, adjusting that route if the passenger's position changes significantly while en route.

**Quick ETA.**
This section lists the three soonest-arriving buses, ranked purely by how soon each is expected to arrive rather than by physical distance or any other ordering. For each listed bus, the displayed arrival estimate preferentially comes from the same dispatch-based estimation the rest of the system's scheduling relies on, which accounts for more than simple straight-line distance; only when that more sophisticated estimate is not yet available for a given bus does the interface fall back to a simpler estimate calculated directly from the straight-line distance between the bus's last known position and the passenger's own location. It is worth noting that this is one of at least two distinct arrival-time calculations appearing in the interface — the number shown when a bus marker's own pop-up is opened directly on the map is calculated independently and may not always exactly match the figure shown in this list, since the two draw from different parts of the system's estimation logic.

**Bus Information Card.**
Each bus card displays a specific set of fields, and it is useful to state plainly where each one actually comes from. The bus's displayed name is its assigned bus number as registered by the administrator, falling back to its internal identifier only if no number was ever assigned. The "ACTIVE" status shown is the same administrator-set operational status used in the Administrator Module's own bus registry — it reflects a deliberate status an administrator has set for that vehicle, not a reading of how recent its GPS signal currently is. The estimated arrival time shown on the card is the same preferred, dispatch-based estimate described above. The origin and destination terminal names are resolved from the bus's assigned route whenever the system can successfully match that route to its registered terminals, and fall back to the route's plain label (such as a route number) when it cannot. The "vehicle identifier" field specifically shows the bus's license plate number, not its internal system identifier and not any hardware-device identifier. The maximum seating figure reflects the seat capacity an administrator has configured for that specific bus, defaulting to fifty if none has been set. The boarded-passenger count is calculated from the actual tickets issued for that bus for the current day, excluding any ticket marked as completed or cancelled, and is recalculated directly from those records each time the information is requested rather than being a stored or separately maintained running total.

**Route Details.**
Selecting a bus genuinely changes what the map displays, beyond simply updating the card's text. The system draws that bus's assigned route as a line on the map — explicitly the planned corridor path the bus is expected to follow, never substituted for or confused with the bus's actual live GPS trail — and visually distinguishes the portion of the route already traveled from the portion still remaining, based on the bus's current position along that path. Distinct markers appear at the route's starting point and destination, and the map automatically adjusts its zoom and centering to bring the full selected route into view. If the route information cannot be retrieved, the interface shows a clear loading or error message in the map's header area, with the option to try again, rather than leaving the passenger looking at an unexplained blank state.

**Passenger Capacity and Boarding Information.**
The maximum-seating figure and the boarded-passenger count described above are refreshed automatically approximately every thirty seconds while the tracking page remains open, and each refresh recalculates the boarded count fresh from current ticket records rather than reusing a previously stored figure — meaning the realistic worst-case delay between an actual boarding and it being reflected on this card is on the order of well under a minute, not an indefinitely stale cached number.

**Live Updates and Error Handling.**
Several parts of this interface refresh on their own independent timers — live bus positions roughly every eighteen seconds, terminal and stop information roughly every ninety seconds, the Quick ETA list and its underlying dispatch data roughly every thirty seconds, notifications roughly every twenty-eight seconds, and weather markers, when enabled, roughly every ten minutes — all through the page repeatedly requesting fresh data rather than through a continuously open live connection. Before any data has loaded for the first time, the interface shows an explicit waiting message rather than an empty or misleading display. When a specific bus's GPS position has not been updated recently enough to be considered current, the system does not quietly continue showing its last known position as though it were live; instead, that bus's map pop-up is labeled to indicate its delay information is unavailable due to a stale signal, though the marker itself remains visible on the map rather than being removed. If no buses are currently available to show, the interface distinguishes between two different situations: if an administrator has deliberately taken live operations offline for the day, a clear banner states this directly; if operations are active but simply no buses happen to be dispatched at that moment, the Quick ETA section instead shows a plain waiting message with no buses listed. Finally, it should be noted as a limitation that the interface's handling of a genuinely unreachable backend connection is not entirely consistent across its parts: some areas of the page, such as the terminal and stop loading, will show a visible error message to the passenger, while others, including the live bus positions, the Quick ETA list, and notifications, will silently continue displaying whatever was last successfully retrieved without informing the passenger that this information may no longer be current.

## Documentation Summary

Taken as a whole, the Passenger Tracking Map gives a commuter a single screen from which to see where active buses currently are, judge how soon the next one is likely to arrive, check a specific bus's route, seating, and boarding status before committing to wait for it, estimate a fare for a planned trip, find the nearest terminal, and reach a feedback or lost-item form if needed — all without creating an account. Its map, positions, and fare figures are drawn from the same underlying data the rest of the system relies on, refreshed through frequent automatic polling rather than an instantaneous push connection, and the interface is generally careful to label estimates, refresh timing, and degraded states honestly rather than presenting them as more certain than they are. The one area worth continued attention is the inconsistency in how different parts of the page respond when the backend cannot be reached — a limitation worth being aware of, since a commuter in that specific situation may see outdated information presented with no visible warning that it is no longer current.

**Testing and Verification.**
This documentation was produced entirely through direct inspection of the system's source code, including deliberately verifying which of two existing copies of the passenger application the described interface actually belongs to, before documenting its behavior. No live browser testing of this interface was performed, no automated or service-level tests were run, and no figure, timing interval, or behavior described above was independently confirmed by operating the deployed application directly. Every statement above describes what the implemented code is written to do, not a confirmed live observation.
