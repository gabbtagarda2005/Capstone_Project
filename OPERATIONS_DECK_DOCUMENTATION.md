# Operations Deck (Command Center) — Component Documentation
### Bukidnon Bus Company @BUKSU — Administrator Module

*Every claim below is traced to `Frontend/Admin_Frontend/src/pages/CommandCenterPage.tsx` and its directly linked module pages and components, cross-checked against the corresponding Admin_Backend routes and services. Where a feature's behavior could not be confirmed in code, that limitation is stated explicitly rather than assumed from the interface.*

---

## A. Overview of the Operations Deck

The Operations Deck, titled on-screen as the "Command center," is the Administrator Module's hub page for passenger-facing system controls, live weather context, and operational self-monitoring. Unlike the View Location page, which is dedicated entirely to live GPS tracking, the Operations Deck brings together a single master visibility switch for the entire passenger-facing live-tracking feature, a rolling weather summary for the company's terminal locations, and a navigation hub into four distinct operational modules — passenger feedback intelligence, broadcast messaging, scheduled-maintenance control, and backend system health. Administrators use this page both as a dashboard in its own right (the LIVE toggle and weather summary are visible and interactive directly on this page) and as a launch point into the four deeper modules it links to, each of which is implemented as its own route rather than as an embedded panel.

## B. Explanation of Each Component

**Operations Deck.** The interface displays the heading "Operations deck" as a small eyebrow label immediately above the page's main title. In the implementation, this text is a static string rendered unconditionally at the top of the page — it is not computed, fetched, or personalized in any way, and it does not change based on the state of any other component on the page. Its purpose is purely to identify the page's role as the administrator's entry point for operational, passenger-facing system controls, distinguishing it from the page's own `<h1>` title directly beneath it.

**Command Center.** The heading "Command center" is the page's primary `<h1>` title, paired with the subtitle "Tactical transit mission control · Bukidnon network pulse" directly beneath it. Both strings are static interface text with no dynamic data binding; neither reflects a live count, a status, or any value drawn from the backend. Together they serve as the page's title block, establishing that this page is the administrator's mission-control surface for the fleet as a whole, as distinct from the GPS-specific View Location page or the historical Dashboard page.

**LIVE Status Indicator.** The exact label `LIVE` (or `OFFLINE` when toggled off) is rendered on a clickable button in the page header. This is not a passive status indicator and does not represent the health of any backend service, database connection, or bus GPS device — it is a real, persisted, administrator-controlled feature flag named `operationsDeckLive`, stored in the `admin_portal_settings` MongoDB collection and defaulting to `true`. On page load, the button's state is fetched from `GET` of the admin portal settings and reflects whatever was last saved; clicking it (available to every role except Auditor, whose session disables the control) immediately flips the flag and persists the change through `PUT /api/admin/portal-settings`. The flag has a direct, verified effect on the backend: when set to `false`, the public fleet-buses endpoint (`routes/buses.js`) returns an empty bus list to the Passenger Interface regardless of how many buses are actually transmitting GPS, and the public operations-deck metrics endpoint returns zeroed figures. The interface's own tooltip text states this directly: "When OFFLINE, passengers do not see live buses on the map or buses in Check buses · Fleet registry." It must therefore be documented as a passenger-visibility kill switch for live tracking, not as a diagnostic readout of whether the system's services are actually functioning — a system can be fully healthy on the backend while this flag is set to OFFLINE, and conversely the flag can read LIVE while an unrelated service (database, GPS ingest) is degraded.

**Weather Overlay.** The "Weather overlay" section presents a list of current weather conditions for the company's registered terminal locations. The list of locations itself is not fixed in the interface: on page load, the component first attempts to fetch every registered terminal from `GET /api/locations/coverage`, using each terminal's configured name and coordinates as a weather spot; only if that request fails or returns no terminals does it fall back to a hardcoded three-location default (Malaybalay, Valencia, Maramag). For each resolved location, the component then queries live current-conditions data directly from the client's browser — using the WeatherAPI.com service if an API key has been configured in the frontend's environment, or Open-Meteo's public forecast API otherwise — refreshed automatically every five minutes. This is architecturally distinct from the weather overlay used on the View Location and Commuter Interface maps, which is instead served through a backend-cached proxy endpoint; the Operations Deck's weather cards are fetched client-side, independently, and on their own refresh schedule. Each resulting row displays the location's name, a condition emoji, a short condition label (e.g. "Cloudy"), the temperature in Celsius, and the relative humidity percentage, with a placeholder ellipsis shown for any location whose reading has not yet arrived.

**Don Carlos Weather Card.** The row for "Don Carlos" and its displayed values "☁️ Cloudy," "24.4°C," and "98% humidity" are the live current-conditions reading returned for that location's coordinates at the time the interface was captured, formatted and rounded by the component as described above. Don Carlos is not one of the three hardcoded fallback locations in the codebase; its appearance confirms that, at the time of capture, the live fetch to `GET /api/locations/coverage` succeeded and returned Don Carlos among the administrator's registered terminals. These values should be understood as a snapshot of the interface's own displayed state rather than as independently verified current weather, since no external weather-provider testing was performed as part of producing this documentation.

**Malaybalay Weather Card.** The row for "Malaybalay" and its displayed values "☁️ Cloudy," "22.0°C," and "97% humidity" follow the same data path described above. Malaybalay is additionally one of the three locations in the component's hardcoded fallback list, so it would appear in this panel even if the live terminal-coverage fetch were to fail, though the specific reading shown is still a live value fetched for its coordinates rather than a static figure baked into the fallback list itself.

**Maramag Weather Card.** The row for "Maramag" and its displayed values "☁️ Cloudy," "24.4°C," and "96% humidity" follow the same data path described above. Maramag is also one of the three hardcoded fallback locations, for the same reason noted under Malaybalay.

**Valencia Weather Card.** The row for "Valencia" and its displayed values "☁️ Cloudy," "24.0°C," and "98% humidity" follow the same data path described above. Valencia is likewise one of the three hardcoded fallback locations, for the same reason noted under Malaybalay.

**Feedback Intelligence.** The button labeled with the exact heading "Feedback intelligence" and subtitle "Passenger CSAT, alerts, route hotspots" is a navigation control; clicking it routes the administrator to a separate page (`/dashboard/command/system-feedback`) rather than opening a preview on the hub itself. That destination page is a fully implemented, data-backed dashboard: it retrieves real passenger feedback records from the backend, presents a fleet-wide satisfaction figure, a geographic hotspot map of where feedback originates, and an individually filterable feed of feedback entries — including star ratings, the bus/driver/attendant each entry concerns, flags for entries submitted as part of an SOS event, and a separate category for lost-item reports — refreshed automatically on a roughly thirty-five-second interval. The administrator can therefore review real passenger satisfaction data, route-level concerns, and flagged incidents from this module, not a static or placeholder view.

**Broadcast Center.** The button labeled with the exact heading "Broadcast center" and subtitle "Passenger & attendant notices" is likewise a pure navigation shortcut on the hub page itself — no message composer, preview, or send action is available without first navigating to the destination route (`/dashboard/command/broadcast`). That destination page is a genuine, functional send workflow rather than a preview: it provides a message composition field, a choice of severity level, and a choice of which application(s) — the Passenger app, the Bus Attendant app, or both — should receive the notice, with the in-progress draft persisted locally in the browser between visits. Submitting the form calls a real backend endpoint that dispatches the broadcast and separately logs an administrative audit event recording the action. This module should accordingly be documented as a functional outbound-communication tool, not merely a shortcut or a cosmetic preview of a messaging feature.

**Maintenance Window.** The button labeled with the exact heading "Maintenance window" and subtitle "Deck flag & settings" is a navigation shortcut to a separate module (`/dashboard/command/maintenance`) and does not itself expose any controls on the hub page. The destination page, however, is a genuinely functional, persisted system control rather than a cosmetic flag: it lets an administrator turn a system-wide maintenance mode on or off, independently choose whether that maintenance state blocks the Passenger app, the Bus Attendant app, or both, and set a custom message shown to blocked users, all saved through the same backend portal-settings mechanism used by the LIVE toggle. Saving is restricted to Super Admin accounts and is recorded as an audit event. It must be noted precisely, however, that this is a manually-operated on/off switch — the implementation provides no date- or time-based scheduling; "maintenance window" describes the feature's purpose (temporarily closing part of the system) rather than any automatic start/end behavior, since no scheduling mechanism was found in the inspected code.

**System Health.** The button labeled with the exact heading "System health" and subtitle "Admin API, database, Firebase & mail status" is a navigation shortcut to a module whose internal route is still named `/dashboard/command/fleet-sensors` in the codebase, a naming holdover from an earlier hardware-telemetry panel that has since been removed from this hub; the destination page itself is titled "SYSTEM HEALTH" on-screen and is unrelated to bus hardware telemetry. That destination page combines four components: a live network-status panel that polls the Admin Backend's own `/health` endpoint approximately every eight seconds and reports, individually, whether the Admin API, MongoDB, the Firebase Realtime Database, and outbound SMTP mail are reachable or configured, alongside secondary figures for Socket.IO connection count, SMS-gateway and authentication-service configuration, report-generation availability, recent GPS-ingest activity, and server CPU/memory/uptime; a real, measured API-endpoint latency and error-rate table drawn from requests actually observed by the backend during its current run, with no simulated figures; a system-events panel; and a traffic-provider status card. One control on this page is cosmetic rather than functional and should be documented as such: the "Re-sync" button shown when the Admin API is reported offline only displays a locally generated confirmation message and does not itself trigger a new health check beyond the panel's own regular eight-second polling cycle. With that single exception, this module should be described as a verified, live connectivity and performance check against real backend signals, not a static configuration summary.

## E. Final Documentation Summary

The Operations Deck differs from the View Location and Dashboard pages in a specific and important way: its primary on-page control, the LIVE/OFFLINE toggle, is not a system-health readout but a real, persisted administrative switch that determines whether the Passenger Interface is shown any live buses at all — a distinction that should be preserved carefully in any written description, since the two are easy to conflate from the interface alone. Its weather panel, while visually similar to the one on the View Location page, is implemented independently, fetching directly from a client-side weather provider on its own five-minute cycle rather than through the backend-cached feed used elsewhere. Of its four linked modules, three are genuinely functional operational tools rather than previews — Feedback Intelligence surfaces real passenger data, Broadcast Center genuinely sends messages to live apps, and Maintenance Window genuinely locks the Passenger and/or Bus Attendant apps system-wide — while the fourth, System Health, is a legitimate, live-polled verification of backend connectivity with exactly one cosmetic exception, its non-functional "Re-sync" button. No behavior described above could not be verified in the inspected source; the one caveat worth restating in any formal defense of this page is that the specific weather readings quoted for Don Carlos, Malaybalay, Maramag, and Valencia are a point-in-time snapshot of the interface as supplied for this documentation, not a figure independently re-verified against the weather provider at the time of writing.
